# 慢段恢复可感知 + 空响应窗口实测 + 诊断行补齐

日期：2026-11-01
前置：docs/superpowers/specs/2026-10-31-playinfo-empty-recovery-design.md（0.1.13 已随 PR #39 合入并发布）；上游 issue #41（0.1.13 发布约 2 小时后再次反馈播放接口空响应，OPEN）。
分支：fix-slow-recovery-visibility（从最新 main 拉出）。

## 背景

1. 0.1.13 的双层重试在结构上是完好的（内层每次恢复尝试最多 4 发 host 轮换请求，外层 RecoveryBudget 共 8 次会走到底），但慢段（第 4 次起）等待间隔 30–105 秒、累计约 5 分钟，期间屏幕完全静态：无倒计时、无动画，文案仅在下次尝试失败后才变化。用户无从判断系统仍在工作——真机实测（2026-11-01）在「正在自动恢复 · 第 4/8 次尝试」处等待后退出，误以为已停止。
2. issue #41（SynchPj，2026-10-31）证明服务端空响应窗口在 0.1.13 上仍然出现，但窗口的频率、时长、换路（host 轮换 + 新连接）逃逸率均无数据；RecoveryBudget 是否需要延长应据实测决定，不应拍脑袋。
3. 错误反馈覆盖不均：诊断行 detail 字段目前只填空响应一种（`EmptyPlaybackResponseException.detail`）；HTTP 状态码（`ContentHttpException.statusCode`）、服务端业务码（「播放接口暂不可用（错误码 x）」）、ExoPlayer 错误码（`errorCodeName`）均未结构化进入诊断行；`playbackFailureSummary` 的 known 清单存在漏网类别——「没有电视可播放的清晰度，请稍后再试或选择其他剧集」「视频服务器不支持分段读取（HTTP x）」落入兜底文案「播放数据读取失败」，恰好是最需要说清楚的"清晰度不支持"类错误。

## 目标行为

1. 恢复等待期间快慢段文案都带逐秒倒计时，消除「画面死了」的错觉：
   - 快段：`播放信息接口返回空响应\n准备恢复播放 · 2 秒后重试 2/8 · 12:34`（数字逐秒刷新，秒数向上取整）
   - 慢段：`播放信息接口返回空响应\n服务暂时没有响应，正在自动恢复 · 30 秒后第 5/8 次尝试 · 12:34`
   - 终局与恢复成功文案不变。
2. Probe.kt 新增 `--soak [分钟]` 采样模式（默认 45）：每 5 秒一轮 × 3 条路径（主 host 池化连接 / 主 host 新连接 / 备用 host hl 新连接，与线上重试策略及既有 --issue38 窗口捕捉三路径一一对应），实时打印窗口命中行，末尾输出聚合摘要：窗口簇数、每簇持续时间、簇内哪条路径先逃逸、总空响应率、最长窗口。输出脱敏沿用 `--issue38` 模式：只含计数与 host 代号（b/hl/lf）。
3. 预算判据（数据驱动，提前定死）：采样捕捉到任一窗口「从首次空响应到最优路径恢复」持续 > 4 分钟 → 慢段尾部加 120s/180s 两档（DELAYS_MILLIS 8→10 项，总覆盖约 9.5 分钟）；窗口均 < 4 分钟或当晚未复现 → 预算不动，如实记录结论。
4. 诊断行 detail 结构化补齐：`diagnosticDetail(problem)` 从异常链提取紧凑键值对（详见组件与改动），开发拿到用户截图即可定位错误类别与关键参数；known 清单补齐后用户文案不再落入兜底。
5. 其余行为不变：解码降档、断网等待、睡眠模式、恢复成功 Toast、返回选集即停止。

## 组件与改动

- **app**（MainActivity.kt）：`scheduleRecovery()` 启动每秒一次的 countdown runnable，仅按 `scheduledAt + delay - now` 计算剩余秒数并更新 `playbackText`，不触碰 `postDelayed` 调度权；`cancelRecovery()` 一并移除该 runnable；HUD 显隐行为零改动。
- **app**（PlaybackRecoveryUi.kt）：`recoveryStatusText` 的 `delayMillis` 入参改为剩余秒数（或等价新增纯函数），快慢段格式统一如上；纯函数保持可单测。
- **app**（PlaybackSources.kt）：新增纯函数 `diagnosticDetail(problem: Throwable): String?`——遍历异常链（≤8 层）提取：`EmptyPlaybackResponseException` → detail 原样（如 `空响应x4 host=b,hl,lf,b`）；`ContentHttpException` → `http=503`；`PlaybackException` → `exo=DECODING_FAILED`（去 `ERROR_CODE_` 前缀）；多项以 `·` 连接，60 字符截断。`playerFailure` 的 detail 提取改用该函数。`playbackFailureSummary` known 清单改前缀匹配并补「没有电视可播放的清晰度」「视频服务器不支持分段读取」两类。
- **core**（Probe.kt）：新增 `--soak` 模式，复用 `--issue38` 骨架（固定剧目、ep8、sessionA）；不改 ContentRepository 线上行为。
- **core**（可选，仅当判据命中）：`RecoveryBudget.DELAYS_MILLIS` 尾部加 120s/180s，`WatchingTest` 补序列断言。
- **README**：播放失败行为段落同步（慢段倒计时、诊断行新 detail 格式；预算若变一并同步）。

## 错误处理

- countdown runnable 只读状态、只更新文本，调度权仍在 `scheduleRecovery()/retryRunnable`；重进 `playerFailure` 时旧 runnable 随 `cancelRecovery()` 移除，无竞态。
- `diagnosticDetail` 与诊断行拼接全程 try/catch 兜底，不因诊断引入新失败路径；不暴露 Cookie、地址、签名参数与凭据。
- known 清单前缀匹配避免长文案精确匹配脆弱；补齐不改现有类别的匹配顺序与文案。
- `--soak` 全程脱敏：只打印计数、host 代号与档位元数据。

## 测试

- 自动化全套：`:core:test :app:testDebugUnitTest :app:assembleDebug :app:lintDebug`。
- app 单测：倒计时文案（快/慢段、秒数取整、终局不倒计时）；`diagnosticDetail` 各异常类型、组合、截断、脱敏（断言不含 `Cookie`、`https://`）；`playbackFailureSummary` 补齐类别不再落入兜底。
- core 单测：预算若延长则补 DELAYS 序列与 total 断言；`PlayRetryPlan` 不动则现有测试即回归。
- 探针：`--issue38` 快筛一次（约 12 分钟）；晚间 `--soak 45` 密集采样（约 1600 发轻量请求，峰值 0.6 发/秒）；结论追加到本文档「附录：采样结论」。
- 真机验收（用户执行）：制造失败观察快/慢段倒计时逐秒刷新与终局文案；错误页诊断行新 detail 格式；恢复成功提示回归。

## 风险与回退

- 每秒刷新仅一次 TextView 赋值，主线程开销可忽略；不新增网络请求。
- `--soak` 请求量约 1600 发，高于上一轮探针（160 发/10 分钟）一个量级，均为既有探测构造；若担心观感可将分钟数参数调低（如 `--soak 30`）。
- 回退 = revert 单个 PR；debug 期间 versionName/versionCode 保持不变，正式发版走统一发布入口。

## 不做的事

- 不做后台持续探测、环形进度等恢复体验重做（对分钟级窗口过度设计）。
- 不做非播放链路（搜索/详情/榜单）的诊断行扩展与文案补齐（另开一轮）。
- 不做稳定错误码体系重构（core 异常体系、异常消息文案不动）。
- 不做诊断二维码（沿用 0.1.13 决策）。
- 不做身份轮换、时钟纠偏、UA/指纹对抗（上轮实测已排除）。

## 附录：采样结论

### 快筛（2026-11-01 00:47，`--issue38`，35 轮 × 3 路径共 105 发）

全部正常，零空响应复现：ep1/ep8 两档位、三个备用 host、端到端 streamLadder（5 档 bytevc1）均 200/code=0；bogus 分集 id 返回 `code=101000` JSON 而非空 body。与既有结论一致：空响应是**成簇的间歇窗口**，非高峰凌晨时段未复现。

### 高峰密集采样（2026-11-01 19:35–20:20，`--soak 45`）

736 轮 × 3 路径共 **2208 发，零空响应、零窗口簇**（rate=0.0%）。昨晚 issue #41 报障的同一时段（约 20:02）今晚完全干净——空响应窗口**不是高峰时段的规律现象**，而是偶发的服务端异常事件（成簇出现、数小时到数天内随机分布）。判据未命中：RecoveryBudget 维持 8 次不变，窗口复发时的防御继续依赖慢段五分钟覆盖与换路重试。

### 晚间密集采样（2026-11-01 21:00–21:45，`--soak 45`，撞上活的空响应事件）

**事件时间线**（两次并行 `--issue38` 探针提供交叉证据）：

| 时刻 | 身份 | 结果 |
|---|---|---|
| 21:00–21:45 | soak 身份 A（事件开始瞬间注册） | **2310/2310 全空，45 分钟零恢复**（770 轮 × 3 路径：主 host 池化/主 host 新建/备 host hl 新建全部无效）|
| 21:02–21:05 | 全新身份 A' | 全部成功（含 34 轮三路径捕捉 0 空）|
| 21:09–21:12 | 全新身份 A'' | **全部为空**（hl/lf/c 同样空，108/108）|
| 21:11–21:12 | 另两个全新身份 B、C | 全部成功（B1/B2/B3/C1 + e2e）|
| ~21:47 | 全新身份 | 全部成功（事件已结束）|

**结论**（修正 10-31 探针「与身份无关」的判断）：

1. 事件为服务端异常窗口（~21:00–21:47，约 47 分钟），期间**按设备身份选择性返回空响应**：被影响身份在所有域名、所有连接模式下 100% 空，且贯穿事件全程（身份 A ≥45 分钟）；未影响身份同刻完全正常。受影响子集随事件推进扩大（21:02 仅 A 中招，21:09 起 A'' 也中招）。
2. **换域名 + 新连接对被屏蔽身份完全无效**（0.1.13 换路策略的边界）；同刻全新身份可即时成功（三次独立验证：A'、B/C、终检）。
3. 对被屏蔽用户，0.1.13 慢段约 6 分钟覆盖必然耗尽 → 终局文案 → 用户稍后手动重试（事件结束）成功——与全部真实用户反馈吻合。
4. **预算判据处置**：窗口 45 分钟形式上命中「>4 分钟」判据，但延长慢段（+120s/180s ≈ 9.5 分钟覆盖）对 45 分钟级身份屏蔽杯水车薪——判据前提「窗口可等待」被本轮数据推翻。预算维持 8 次不变，长窗口的正解是**身份轮换自愈**（见下），留待下一设计轮处理。

### 后续方向（待用户决策）

**身份轮换自愈**：恢复流程在换路重试连续全空后（强信号 = 非瞬时故障），重新注册一次匿名设备身份再续播。需设计：触发阈值（如快段耗尽且内层 4 发全空 ≥2 轮）、轮换上限（每集至多 1 次，防滥用轮换）、与会话/账号数据隔离、注册失败回退慢段。本轮数据为其证据基线。
